# Chat

[![CI](https://github.com/TaronMin/two-panel-chat/actions/workflows/ci.yml/badge.svg)](https://github.com/TaronMin/two-panel-chat/actions/workflows/ci.yml)

**▶ Live demo: <https://taronmin.github.io/two-panel-chat/>**

One conversation, rendered simultaneously from both sides. The left panel is the **User**;
the right panel is the **Answerer**, who can either type a reply or have one generated by
a free AI provider.

The two panels are genuinely two clients. Each opens its own WebSocket and joins the same
room, so presence, typing indicators and read receipts mean something — it is not one
array rendered twice.

> The demo runs on free hosting that sleeps when idle. The first visit after a quiet spell
> can take ~50s while the API wakes up; reload if the page reports it cannot reach the
> backend.

---

## What it does

- **Live two-way chat** over a Nest.js socket.io hub — messages, typing, presence and
  delivery/read receipts.
- **AI answerer** with three modes: draft-and-review, auto-send, or fully automatic
  replies to every incoming message.
- **Edit and delete** your own messages, with soft-deleted tombstones.
- **Chat history** — every conversation this browser has started, switchable from a sidebar
  on desktop or a slide-over drawer on mobile.
- **Markdown rendering** for AI replies, sanitised on the way into the DOM.
- **Responsive** — side-by-side on desktop, tabbed panels on mobile.

**Stack:** Nest.js · socket.io · Angular (standalone components, signals) · Tailwind CSS

```
├── server/   Nest.js — hub, REST API, services, pluggable AI
└── client/   Angular + Tailwind
```

## Running it locally

Node 24+ (the lock files are generated with npm 11).

```bash
# terminal 1
cd server && npm install && npm run start:dev    # http://localhost:3000

# terminal 2
cd client && npm install && npm start            # http://localhost:4200
```

Start the backend first — the frontend creates a conversation over REST on load.

For real AI replies, copy `server/.env.example` to `server/.env` and add a free Groq key
(see [AI providers](#ai-providers)). Without one the app still runs, answering from an
offline mock provider.

## How it works

### Sending is REST; receiving is the socket

This surprises people, so it is worth stating plainly: **the sender does not emit its
message on the socket.** It POSTs, and the server broadcasts.

```
User panel                    SERVER                      Answerer panel
    │                            │                             │
    ├── POST /messages ─────────►│                             │
    │                            ├─ appendMessage()            │
    │                            ├─ emit "message:new" ───────►│ renders
    │◄── "message:new" ──────────┤  to the room                │
    │◄── 200 OK {message} ───────┤                             │
```

The sender receives its own message twice — once from the HTTP response, once from the
broadcast — and `applyMessage` de-duplicates by id. That is deliberate: the sender gets
instant feedback without waiting on the socket, and a duplicate never appears.

HTTP handles the write because it gives real status codes and validation errors to await.
The socket handles everything *pushed*: new messages, edits, typing, presence, receipts,
mode changes and AI generation state.

### Storage

There is no database. Conversations and messages live in a `Map` in
`server/src/chat/services/message-store.service.ts`, so restarting the server clears
everything. The browser remembers the conversation the tab has open in `sessionStorage` and
quietly starts a new one when the server no longer recognises it.

### Chat history

The server has no accounts, so history is scoped to the browser rather than to a user:
`ChatHistoryService` keeps the conversations this browser started in `localStorage` and
looks each one up through `GET /:id/state`. That deliberately avoids building the switcher
on `GET /api/conversations`, which returns *every* visitor's conversation and would expose
them to each other on the shared demo.

Each entry caches a label, preview and timestamp so the list paints before the network
answers; a background refresh then corrects them. Labels come from the first user message,
because the stored title is the same for every conversation. A conversation the server has
forgotten is pruned on a `404` — and only on a `404`, so an offline blip cannot wipe the
list. Removing an entry drops it locally; it does not delete anything server-side.

### The answerer's modes

A segmented `Manual | AI` toggle, persisted per browser session and synced over the hub so
both panels agree.

| Auto-answer | Auto-send | Behaviour |
|---|---|---|
| off | off | Click *Generate*, review the draft, send |
| off | on | Click *Generate*, the reply goes straight out |
| on | *forced on* | Replies automatically whenever the user writes |

An optional free-text steer ("keep it short and apologetic") is passed to the provider.

While a reply generates, the answerer's composer and mode toggle lock, and the user sees an
ordinary typing indicator. AI replies are badged as AI **only in the answerer's own
panel** — to the user they read as a normal message.

### Editing and deleting

Either side can edit or delete its own messages. Deletes are soft: the row stays as a
"This message was deleted" tombstone, the text is dropped, and deleted messages are
excluded from the history sent to the AI.

## AI providers

Everything runs through one interface, `server/src/ai/ai-provider.interface.ts`. Set
`AI_PROVIDER` in `server/.env` plus the matching key:

| `AI_PROVIDER` | Cost | Default model | Key variable | Get a key |
|---|---|---|---|---|
| `groq` (recommended) | **free tier** | `openai/gpt-oss-120b` | `GROQ_API_KEY` | <https://console.groq.com/keys> |
| `openrouter` | **free tier** | pick a current `:free` id | `OPENROUTER_API_KEY` | <https://openrouter.ai/keys> |
| `gemini` | **free tier** | `gemini-2.0-flash` | `GEMINI_API_KEY` | <https://aistudio.google.com/apikey> |
| `pollinations` | free, no key | `openai-fast` | — | none needed |
| `xai` (Grok) | paid | `grok-3-mini` | `XAI_API_KEY` | <https://console.x.ai> |
| `openai` | paid | `gpt-4o-mini` | `OPENAI_API_KEY` | <https://platform.openai.com/api-keys> |
| `anthropic` | paid | `claude-opus-5` | `ANTHROPIC_API_KEY` | <https://console.anthropic.com> |
| `mock` | free, offline | heuristic | — | canned replies, no network |

> **Pinned model names go stale.** Vendors retire models without warning; the provider then
> returns `404 model_not_found`, which `AiService` turns into a silent fallback to mock. If
> replies suddenly read like canned filler, suspect the model name before the key and check
> the server log for `Provider "<name>" failed`.

Override the model with `AI_MODEL` and the host with `AI_BASE_URL`. Other knobs:
`AI_PERSONA`, `AI_MAX_TOKENS`, `AI_TIMEOUT_MS`.

Everything except Anthropic speaks the same `/chat/completions` shape, so they share
`providers/openai-compatible.provider.ts`, driven by the table in
`providers/provider-presets.ts`. **Adding a vendor:** if it is OpenAI-compatible, add a row
there and you are done.

If the provider is missing a key, times out or throws, `AiService` falls back to the mock
provider — a dead vendor degrades the suggestion instead of breaking the chat. The draft
box names the provider and model that actually answered, so a canned reply is traceable.

## Deploying

The client is static and the server is not, so they deploy separately.

```
visitor ──► taronmin.github.io/two-panel-chat     static client (GitHub Pages)
                     │
                     │  REST + WebSocket
                     ▼
            <api-host>.onrender.com               Nest + AI key
```

**1. Server.** `render.yaml` describes the service — on Render pick *New → Blueprint* and
point it at this repo. Set two variables in the dashboard (deliberately not in the repo):

| Variable | Value |
|---|---|
| `GROQ_API_KEY` | your key |
| `CORS_ORIGIN` | `https://<you>.github.io` — origin only, no path |

Any Node host works: the server reads `PORT` and binds `0.0.0.0`.

**2. Client.** Put the deployed origin in `client/src/environments/environment.prod.ts`.
Production builds swap it in via `fileReplacements`; local development keeps
`http://localhost:3000`.

**3. Pages.** *Settings → Pages → Source → GitHub Actions*. Pushing to `main` runs
`.github/workflows/deploy-client.yml`, which builds with the right `--base-href` for a
project site and publishes.

Never commit `server/.env` — it is git-ignored, and keys belong in the host's dashboard.

## Architecture

**SignalR-style hub** (`server/src/hub/`) — `HubBase` gives a Nest gateway the shape of a
hub: `onHubInitialized` / `onConnectedAsync` / `onDisconnectedAsync` lifecycle hooks,
`groups.addToGroupAsync(connectionId, group)`, and single-client dispatch via
`clients.client(...)`. `ConnectionManager` tracks live connections and their group
membership. Room-wide fan-out goes through `ChatBroadcastService`, so `ChatGateway` only
handles chat events.

**Services** (`server/src/chat/services/`):

- `MessageStore` — in-memory persistence.
- `ChatBroadcastService` — the only place domain events are pushed to clients. Keeping it
  out of the gateway is why a message created over REST still reaches both panels.
- `PresenceService` — volatile per-conversation state: who is connected, who is typing,
  the answerer's mode.
- `ConversationService` — orchestration. Gateway and controllers both funnel through it,
  so the two transports cannot drift apart.

**Client** (`client/src/app/`) — state is Angular signals; `SocketService` exposes typed
RxJS observables per event; `ChatApiService` wraps REST; composers are reactive forms.

```
components/
├── chat-container/     both panels, shared chrome, mobile tabs
├── user-panel/         the user's perspective
├── answerer-panel/     the answerer's perspective + AI controls
├── message-thread/     scrolling list with auto-scroll
├── message-bubble/     one message, viewer-relative, edit/delete
├── markdown-content/   sanitised markdown rendering
└── mode-toggle/        Manual | AI segmented control
```

## Reference

### REST

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/conversations` | Create a conversation |
| `GET` | `/api/conversations` | List conversations |
| `GET` | `/api/conversations/:id` | One conversation |
| `GET` | `/api/conversations/:id/state` | Snapshot: conversation, history, mode, presence |
| `GET` | `/api/conversations/:id/messages?limit=50` | History |
| `POST` | `/api/conversations/:id/messages` | Send — this is what the UI calls |
| `POST` | `/api/conversations/:id/suggestions` | Generate — `{ instruction?, autoSend? }` |
| `GET` | `/api/ai/provider` | Active provider and whether it is configured |

### Hub events

Namespace `/chat`, one room per conversation (`conversation:<id>`). Types live in
`server/src/chat/contracts/`, mirrored at `client/src/app/core/contracts.ts`;
`ChatServerEvents` maps every event to its payload, so a mismatched payload is a compile
error on both sides.

| Client → server | Server → client |
|---|---|
| `conversation:join` *(acked)* | `connection:established` |
| `conversation:leave` | `conversation:state` |
| `message:edit` *(acked)* | `message:new` |
| `message:delete` *(acked)* | `message:updated` |
| `typing:start` / `typing:stop` | `typing:update` |
| `answerer:mode-change` | `answerer:mode-changed` |
| `message:read` | `presence:update` |
| | `message:receipt` |
| | `ai:generating` |

`message:updated` carries both edits and deletes — `editedAt` / `deletedAt` say which.

All socket payloads and REST bodies are `class-validator` DTOs behind a global
`ValidationPipe`.

### Data model

```ts
Conversation { id, title, createdAt, participants: ('user' | 'answerer')[] }

Message {
  id, conversationId,
  sender: 'user' | 'answerer',
  content,                    // emptied when deleted
  mode: 'manual' | 'ai',
  createdAt,
  status: 'sent' | 'delivered' | 'read',
  generatedBy?,               // provider name, when mode === 'ai'
  editedAt?,
  deletedAt?,                 // set = render a tombstone
}
```

### Tests

| Location | Command | Covers |
|---|---|---|
| `server` | `npm test` | Unit — `src/**/*.spec.ts` |
| `server` | `npm run test:e2e` | End-to-end — `test/*.e2e-spec.ts` |
| `server` | `npm run test:cov` | Unit tests with coverage |
| `client` | `npm run test:ci` | Unit — `src/**/*.spec.ts`, once and exit |
| `client` | `npm test` | The same, in watch mode |

Server unit tests cover the store's tombstone semantics, the presence service's
multi-connection bookkeeping, `ConversationService` orchestration — including that a failed
generation still clears the typing and `ai:generating` flags — and `AiService` degrading to
the mock provider when the vendor is unconfigured or throws.

The e2e suite boots the real `AppModule` on an ephemeral port with `AI_PROVIDER=mock` and
drives it through two live socket.io clients, so the REST-write / socket-read split above is
asserted rather than described: a message POSTed by one panel has to arrive at the other over
the wire. `test/app.factory.ts` is the shared harness.

Client tests run on the Angular `unit-test` builder with vitest and jsdom. They cover the
markdown sanitiser's handling of `javascript:`/`data:`/`vbscript:` hrefs, the connection
registry's aggregation, `PanelChatService` — including the send/broadcast de-duplication
described above — and the answerer panel's auto-answer effect, which must still answer a
message that arrived while the previous reply was generating.

CI (`.github/workflows/ci.yml`) runs lint, build and both test suites for each package on
every push and pull request. The Pages deploy runs the client tests first, so a failing test
blocks the release.
