# Two-Panel Chat

One conversation, rendered simultaneously from both sides. The left panel is the **User**;
the right panel is the **Answerer**, who can either type a reply or have one generated by
a free AI API.

Messages are sent over the REST API and pushed to both panels over a Nest.js WebSocket
gateway built to mirror SignalR's hub patterns — connection lifecycle hooks, group
membership, and typed message contracts.

```
Chat/
├── server/   Nest.js — gateway, REST API, services, pluggable AI
└── client/   Angular (standalone components) + Tailwind CSS
```

## Running it locally

Two terminals. Node 20+ required (developed on Node 24).

**Terminal 1 — backend**

```bash
cd server
npm install
npm run start:dev        # http://localhost:3000
```

**Terminal 2 — frontend**

```bash
cd client
npm install
npm start                # http://localhost:4200
```

Open <http://localhost:4200>. Start the backend first — the frontend creates a
conversation over REST on load.

Copy `server/.env.example` to `server/.env` and add a free Groq key — see
[Configuring the AI provider](#configuring-the-ai-provider). Without one the app still
runs, answering from the offline mock provider.

## Deploying

The client is static and the server is not, so they deploy to different places: the
Angular build goes to GitHub Pages, the Nest server to any host that runs Node.


**1. Deploy the server.** `render.yaml` in the repo root describes the service, so on
Render you can pick *New → Blueprint* and point it at the repo. Set two variables in the
dashboard (they are deliberately not in the repo):

| Variable | Value |
|---|---|
| `GROQ_API_KEY` | your key from <https://console.groq.com/keys> |
| `CORS_ORIGIN` | `https://<you>.github.io` |

Any Node host works — the server reads `PORT` and binds `0.0.0.0`. Free tiers usually
sleep when idle, so the first request after a quiet period can take ~50s.

**2. Point the client at it.** Put the deployed origin in
`client/src/environments/environment.prod.ts`:

```ts
export const environment = {
  production: true,
  apiBaseUrl: 'https://your-api-host.onrender.com',
};
```

Production builds swap this in via `fileReplacements`; local development keeps using
`http://localhost:3000`.

**3. Enable Pages.** In the repo: *Settings → Pages → Source → GitHub Actions*. Pushing to
`main` then runs `.github/workflows/deploy-client.yml`, which builds with the correct
`--base-href` for a project site and publishes.

Never commit `server/.env` — it is git-ignored, and the key belongs in the host's
dashboard.

## Storage

There is no database. Conversations and messages live in a `Map` inside
`server/src/chat/services/message-store.service.ts`, so restarting the server clears
everything. The browser remembers its conversation id in `sessionStorage` and quietly
starts a new one when the server no longer knows it.

## Message flow

Sending is an **HTTP call**, not a socket emit. When either panel sends:

1. `POST /api/conversations/:id/messages` persists the message in the in-memory store.
2. The server broadcasts `message:new` to the conversation group.
3. Both panels render it — the sender's panel included.

The socket carries everything that is *pushed*: new messages, typing, presence, receipts,
mode changes and AI generation state.

**User** types and sends — manual only.

**Answerer** has a segmented `Manual | AI` toggle, persisted per browser session and
synced over the hub so both panels agree on the current mode.

- **Manual** — an ordinary composer.
- **AI** — "Generate reply" drafts a response from the thread. The default is
  **review-before-send**: the draft lands in an editable box with *Send reply*,
  *Regenerate* and *Discard*, and nothing reaches the conversation until it is sent.
  Ticking **Auto-send without review** posts each generation straight to the thread.
  Ticking **Auto-answer new messages** replies on its own whenever the user writes; it
  implies auto-send, since nobody is waiting to review an unattended reply.
  An optional free-text steer ("keep it short and apologetic") is passed to the provider.

While a reply is generating, the answerer's composer and mode toggle lock, and the user
sees an ordinary typing indicator. AI replies render markdown and are badged as AI only in
the answerer's own panel — to the user they read as a normal message.

Either side can **edit or delete its own messages** (pencil / trash on the bubble). Deletes
are soft: the row stays as a "This message was deleted" tombstone, the text is dropped, and
deleted messages are excluded from the history sent to the AI.

## Configuring the AI provider

Everything runs through one interface — `server/src/ai/ai-provider.interface.ts`:

```ts
interface AiSuggestionProvider {
  readonly name: string;
  readonly model?: string;
  isConfigured(): boolean;
  generate(context: AiSuggestionContext): Promise<AiSuggestion>;
}
```

Copy `server/.env.example` to `server/.env` and set `AI_PROVIDER` plus the matching key:

| `AI_PROVIDER` | Cost | Default model | Key variable | Get a key |
|---|---|---|---|---|
| `pollinations` | **free, no key** | `openai-fast` | — | none needed |
| `groq` (recommended) | **free tier** | `openai/gpt-oss-120b` | `GROQ_API_KEY` | <https://console.groq.com/keys> |
| `openrouter` | **free tier** | see note below | `OPENROUTER_API_KEY` | <https://openrouter.ai/keys> |
| `gemini` | **free tier** | `gemini-2.0-flash` | `GEMINI_API_KEY` | <https://aistudio.google.com/apikey> |
| `xai` (Grok) | paid | `grok-3-mini` | `XAI_API_KEY` | <https://console.x.ai> |
| `openai` | paid | `gpt-4o-mini` | `OPENAI_API_KEY` | <https://platform.openai.com/api-keys> |
| `anthropic` | paid | `claude-opus-5` | `ANTHROPIC_API_KEY` | <https://console.anthropic.com> |
| `mock` | free, offline | heuristic | — | canned replies, no network |

> **Pinned model names go stale.** Vendors retire models without warning, and the provider
> then returns `404 model_not_found`, which `AiService` turns into a silent fallback to the
> mock provider. If replies suddenly read like canned filler, suspect the model name before
> the key, and check the server log for `Provider "<name>" failed`. The OpenRouter preset in
> particular needs a current `:free` model id from <https://openrouter.ai/models>.

**Use Groq** — free, fast, and reliable:

```env
AI_PROVIDER=groq
GROQ_API_KEY=gsk_...
```

Override the model with `AI_MODEL` and the host with `AI_BASE_URL`. Other knobs:
`AI_PERSONA`, `AI_MAX_TOKENS`, `AI_TIMEOUT_MS` (default 60s).

All of these except Anthropic speak the same `/chat/completions` shape, so they share one
implementation (`providers/openai-compatible.provider.ts`) driven by the table in
`providers/provider-presets.ts`. Anthropic uses its own SDK.

**Adding a vendor**: if it is OpenAI-compatible, add a row to `provider-presets.ts` and
you are done. Otherwise implement the interface and add a branch to `createProvider()` in
`server/src/ai/ai.module.ts`.

If the configured provider is missing a key, times out or throws, `AiService` falls back to
the mock provider so a dead vendor degrades the suggestion instead of breaking the chat.
The failure is logged server-side; in the UI the draft box names the provider and model
that actually answered, so a canned-sounding reply can be traced.

## Real-time contract

The gateway namespace is `/chat`, with one group (socket.io room) per conversation:
`conversation:<id>`. Event names and payload types live in `server/src/chat/contracts/`,
mirrored on the client at `client/src/app/core/contracts.ts`. `ChatServerEvents` maps every
event name to its payload, and both the server's `clients.group(x).send(...)` and the
client's `socket.on(...)` are generic over it, so a mismatched payload is a compile error.

| Client → server | Server → client |
|---|---|
| `conversation:join` *(acked)* | `connection:established` |
| `conversation:leave` | `conversation:state` |
| `message:edit` *(acked)* | `message:new` |
| `message:delete` *(acked)* | `message:updated` |
| `typing:start` / `typing:stop` | `typing:update` |
| `answerer:mode-change` | `answerer:mode-changed` |
| `message:read` | `presence:update` |
| | `message:receipt` |
| | `ai:generating` |

Sending goes over REST; editing and deleting go over the hub with acks. `message:updated`
carries both edits and deletes — `editedAt` / `deletedAt` on the message say which.

Also implemented: typing indicators for both roles, a connection indicator
(connected / reconnecting / disconnected), automatic rejoin after a dropped socket, and
delivery/read receipts.

### Why each panel has its own socket

The two panels are two participants, so each opens its own connection and joins the same
group. What you see side by side is genuinely two clients kept in sync by the hub, not one
array rendered twice — which is what makes per-role presence, typing and receipts mean
anything.

## REST API

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/conversations` | Create a conversation |
| `GET` | `/api/conversations` | List conversations |
| `GET` | `/api/conversations/:id` | One conversation |
| `GET` | `/api/conversations/:id/state` | Snapshot: conversation, history, answerer mode, presence |
| `GET` | `/api/conversations/:id/messages?limit=50` | History retrieval |
| `POST` | `/api/conversations/:id/messages` | Send a message — this is what the UI calls |
| `POST` | `/api/conversations/:id/suggestions` | Generate a suggestion — `{ instruction?, autoSend? }` |
| `GET` | `/api/ai/provider` | Which provider is active, and whether it is configured |

All socket payloads and REST bodies are `class-validator` DTOs
(`server/src/chat/dto/chat.dto.ts`) behind a global `ValidationPipe`.

## Architecture notes

**SignalR-style hub** (`server/src/hub/`) — `HubBase` gives a Nest gateway the shape of a
hub: `onHubInitialized` / `onConnectedAsync` / `onDisconnectedAsync` lifecycle hooks,
`groups.addToGroupAsync(connectionId, group)`, and single-client dispatch via
`clients.client(...)`. `ConnectionManager` tracks live connections and their group
membership. Room-wide fan-out goes through `ChatBroadcastService` instead.
`ChatGateway` only handles chat events.

**Service layering** (`server/src/chat/services/`):

- `MessageStore` — in-memory persistence.
- `ChatBroadcastService` — the only place domain events are pushed to clients. Keeping it
  out of the gateway is why a message created over REST reaches both panels.
- `PresenceService` — volatile per-conversation state (who is connected, who is typing,
  the answerer's mode).
- `ConversationService` — orchestration. Both the gateway and the controllers funnel
  through it, so the two transports cannot drift apart.

**Frontend components** (`client/src/app/components/`) — one folder per component, each
holding its `.ts` and its external `.html` template:

```
components/
├── chat-container/    ChatContainerComponent   both panels + shared chrome
├── user-panel/        UserPanelComponent       the user's perspective
├── answerer-panel/    AnswererPanelComponent   the answerer's perspective + mode toggle
├── message-thread/    MessageThreadComponent   scrolling list, auto-scroll
├── message-bubble/    MessageBubbleComponent   one message, viewer-relative
└── mode-toggle/       ModeToggleComponent      Manual | AI segmented control
```

Each folder contains `<name>.component.ts` and `<name>.component.html`.

State is Angular signals; `SocketService` exposes typed RxJS observables per event;
`ChatApiService` wraps the REST calls; composers are reactive forms.

## Data model

```ts
Conversation { id, title, createdAt, participants: ('user' | 'answerer')[] }
Message {
  id, conversationId,
  sender: 'user' | 'answerer',
  content,
  mode: 'manual' | 'ai',
  createdAt,
  status: 'sent' | 'delivered' | 'read',
  generatedBy?            // provider name, when mode === 'ai'
}
```
